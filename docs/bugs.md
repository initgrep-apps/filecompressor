## Runner brew nondeterminism class in CI freezes — resolved by homebrew-core pin (2026-10-16)

- **Stale runner index** — macos-15 images ship an old homebrew-core checkout; a freeze without `brew update` resolved old formula versions (vips 8.18.6 / gs 10.07.x era) against a manifest pinning 8.18.7 / 10.08.0, and the drift gate killed the run. The naive `brew update` fix pulled HEAD core instead, whose formula/bottle state nobody tied to the manifest. Resolved: CI never refreshes brew — freeze.yml checks out homebrew-core at the commit pinned for the row's triple (single `scripts/ci/homebrew-core.sha` at the time; now per-arch `scripts/ci/homebrew-core-pins.json`, see the addendum below) and installs off that pinned tap.
- **Missing-bottles source builds** — homebrew-core stopped publishing x86_64 (sonoma-tier) macOS bottles between 2026-09-10 and 2026-09-11 (harfbuzz 14.4.0 bottle `f2fac97b51f2` still carries `sonoma` digests; ghostscript 10.08.0 a day later does not). Fresh-core x86_64 freezes therefore sent the vips/ghostscript closure into hours-long source builds (llvm included); one run hung 6h / ~3600 billed minutes. Resolved for arm64 by the pin (`cb5b5e2230fd` carries fresh arm64_sequoia bottles for both formulas and their closure); the x86_64 facts and options live in ADR 0001 (no commit can supply vips 8.18.7 x86_64 bottles — vips 8.18.7 postdates the tier death by 16 days). Freeze matrix rows are now bounded at 40 min so this class fails loudly and cheaply instead of hanging.
- **Bootstrap red period** — the first 8 workflow runs under the brew-staging model recorded here (oct 2026) ended 0-for-8: two freezes lost to the brew nondeterminism above, the rest failed downstream of the missing/garbled sidecars release. They are the reason the freeze design moved to the pinned-tap + all-triple model in ADR 0001's 2026-10-16 ruling.
- **Addendum (2026-10-16, amended 2026-10-17): x86_64 leg resolved by freezing Intel, not by chasing bottles** — the pin is now per-arch (`scripts/ci/homebrew-core-pins.json`). `x86_64-apple-darwin` pins `c36952de43157c2c4a4ea05f385031aa29f30354` (2026-08-28, parent of the openssl@3 3.6.4 bump; moved 2026-10-17 from the earlier `8f15b0f1b965` pick, which died at `cgif: no bottle available!` because its closure was only partially bottled), the newest commit where the whole 61-formula vips 8.18.6 + gs 10.07.1 macOS closure still carries `sonoma` x86_64 bottles — per-formula bottle deaths began 2026-08-28 (openssl@3 3.6.4) and completed 09-10/11 — and the manifest freezes Intel at exactly those versions (expectVersions stayed vips 8.18.6 / gs 10.07.1 through the pin move). The fully-bottled pin pours the whole Intel closure from sonoma bottles on the Sequoia runner (brew's bottle fallback serves newer macOS from older tags). Intel engines stay frozen there until a human re-verifies bottles — no homebrew-core commit can ever supply vips 8.18.7 / gs 10.08.0 x86_64 bottles.

## Windows-row msys lock-refusal residue — recorded 2026-10-17 (gate runs 39016160897 / 39021164217)

- **Symptom:** on the windows-2025 CI row, `freeze.sh`/`unfreeze.sh` runs that hit the pre-existing-lock path inside `acquire_lock` exit 1 with EMPTY stdout and stderr — both the `fail "another freeze or unfreeze holds the lock …"` line and the stale-recovery `info "removed stale lock from dead pid …"` line never reach the test's pipes. POSIX (mac CI row + local bash 5.2) prints both correctly. Stable across two runs, independent of the 7bfbfa3 arg-POSIX-ization, so the divergence sits in the msys bash lock-path itself, not in argv handling.
- **Disposition:** the five affected tests are `it.skipIf(process.platform === "win32")` with `_win32_skips_lock_refusal_semantics_differ` (matching the `win32_skips_acl_semantics_differ` / `win32_skips_mv_shim_cygpath_followup_tracked` precedent so the runner-portability suite stays green); POSIX coverage is complete on every row that can run them.
- **Next step if ever fixed hands-on:** needs a real win32 shell session (windows runner or a git-bash install) to observe which msys construct inside `acquire_lock` (mkdir fallback → `cat` → `kill -0` → `stat`/`date`/arithmetic → `fail`) swallows the piped output; a candidate probe is running acquire_lock line-by-line under `bash -x` with a pre-created lock dir and a dead pid.
- **Solved in the same gate residue:** `fails_closed_when_tar_is_absent_from_the_path` ENOENT was libuv resolving `bash` through the CHILD env PATH on win32 (the test replaces PATH with an empty dir); fixed by resolving bash absolutely via `where bash` (win32 only) before the env override — POSIX side byte-identical (`/bin/bash`).

## CI runner-environment classes on GitHub-hosted runners — diagnosed & fixed 2026-10-17

Each class is a runner-shell/OS quirk that bit a real freeze/gate/release run during the October 2026 bootstrap (14 freeze attempts; fix ladder in the plan ledger). The fix pattern is now in the code; recorded here because the class — not the one fix — is the durable fact.

- **git-bash mktemp rejects templates without trailing X's** — msys/git-bash `mktemp` (the windows runner's `shell: bash`) fails templates with too few trailing `X`s (`too few X's in template`), killing the freeze/unfreeze DLL scan. Fix pattern: keep trailing `XXXXXX` in every mktemp template (`dll-scan-errors-XXXXXX`) — commit a5c8492, covered by tests.
- **GNU tar drive-colon remote-parse** — git-bash's GNU tar parses a path like `C:/...` as `host:file` (remote-tape syntax), so windows extraction failed with bogus `C:` remote errors. Fix pattern: extract with the native System32 `tar.exe` on win32 (`lib.mjs` `tarToolForHost()`), never via git-bash GNU tar; windows staging/audit take native bsdtar paths throughout.
- **bash 3.2 ERR trap in guarded pipelines** — macOS default `/bin/bash` 3.2 (mac runner default) fires `set -E`'s ERR trap inside constructs bash 5 treats as guarded, so a `||`-protected failure could double-fire the audit's abort reporter. Fix pattern: re-entrancy guard flag (`err_trap_active`) around the ERR trap in `scripts/audit-sidecars.sh` — a trap already running is not re-entered.
- **empty array + `set -u` on bash 3.2** — `"${arr[@]}"` with an empty array is an unbound-variable error on bash 3.2. Fix pattern: expansion guards `${arr[@]+"${arr[@]}"}` (gh args in freeze/unfreeze) or guaranteed non-empty construction (tar arg list) before expansion.
- **brew 7.0.9 keg-message shape** — brew 7.x changed `brew list --versions` output/error shapes for missing formulas (quiet exit, `no such keg` text variants), tripping version-drift parsing on the runner. Fix pattern: verify.mjs classifies `no such keg|not installed` plus empty output as "formula not installed" instead of a parse error; on brew-less CI hosts the audit proceeds only with `BINARIES_ALLOW_INACTIVE_BREW=1`, degrading the drift gate to note lines instead of failing the row.
- **windows test exes died pre-main with 0xc0000139 (`STATUS_ENTRYPOINT_NOT_FOUND`)** — the app's embedded exe manifest (which tauri-build declares for the app target) was absent from `cargo test` executables, so the loader failed activation before `main`. Fix chain: embed `src-tauri/windows-app-manifest.xml` into **every** msvc link via `src-tauri/build.rs` (`/MANIFEST:EMBED` + `/MANIFESTUAC:NO` + `/MANIFESTINPUT`, with `new_without_app_manifest()` so there is no double manifest — commit 783d202), wire loader diagnostics around `cargo test` (d328e4b), and probe the loader via test enumeration instead of a full rerun (a135346). The diagnostics steps stay in ci.yml until the removal decision tracked in `docs/ci-followups.md`.
